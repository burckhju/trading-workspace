## Konkrete Wirkung

Die tatsächliche Kaufwährung wird einmal eingegeben und beim Speichern des Kaufs
mitgespeichert. Der zusätzliche Bestätigungshaken entfällt. Damit wird ein
eingetippter Code nicht mehr unbemerkt aus dem Request weggelassen.

Für Verkäufe und Nachkäufe wird die vollständig belegte gemeinsame Währung der
vorherigen wirksamen Käufe verwendet. Eine erneute Eingabe ist im Normalfall
nicht nötig. Reine Datums-/Preisänderungen übernehmen die vorhandene bestätigte
Währung aus der exakten gleichseitigen Korrekturkette. Tatsächliche Abweichungen
lassen sich weiterhin ausdrücklich angeben; widersprüchliche oder gemischte
Angaben werden nicht überschrieben oder umgerechnet.

Die Herkunft ist in den Buchungen und im Ergebnisbericht sichtbar: direkt
eingegeben oder aus konkreten Kauf-/Korrekturquellen übernommen, jeweils mit
Quellen- und Bestätigungs-IDs. Bestehende Verkäufe mit belegter Kaufwährung
werden dadurch ohne Einzelbestätigung jedes Verkaufs auswertbar.

Für einen älteren Kauf ohne gespeicherte Ausführungswährung bleibt eine echte
Quellenlücke. Eine tatsächliche Kaufwährung kann einmal am ursprünglichen Kauf
ergänzt werden und gilt dann auch für seine nachfolgenden gleichartigen
Buchungen. Ein alter Plan-, Strike- oder Listingwert ersetzt diesen Beleg nicht;
ein früher nie gespeicherter Eingabewert kann nicht rekonstruiert werden.

## Technischer Umfang und Betrieb

Der Execution-Owner löst die Währung rein lesend auf. Er schreibt keine
zusätzlichen vermeintlichen Benutzerbestätigungen für abgeleitete Verkäufe.
Die API ergänzt `currency_resolution`; bestehendes `currency_confirmation`
bleibt die tatsächliche direkte Erklärung. Die Berichtsdefinition ist
**`realized-gross-sell-v2`**. Average Cost, Periodengrenzen, Decimal-Präzision,
Abdeckungszustände und der kurze konsistente Berichtssnapshot bleiben erhalten.

Keine neue Migration: Schema-Head bleibt **`20261017_0047`**. Bestehende
Ausführungen, Bestätigungen, Journal-/Review-/Evidence-Inhalte und private
Konfigurationen werden nicht rückwirkend umgeschrieben. Keine FX-Umrechnung,
Provideranfrage, Modellaktivierung oder automatische Nutzerbestandsänderung
folgt aus diesem Update. Der Schnitt erfüllt weiterhin nicht den gesamten
ursprünglichen M8- oder Depotperformance-Umfang.

## Verwalteten PC aktualisieren

Der bestehende [Linux-Launcher](../technical/LINUX_LAUNCHER.md) und seine privaten
Compose-/Datenpfade bleiben unverändert. Als bisheriger Benutzer ohne sudo
arbeiten. Nach Veröffentlichung den vollständigen, erfolgreich geprüften
Tag-Commit verwenden:

```bash
~/.local/bin/trading-workspace status
git ls-remote --tags https://github.com/burckhju/trading-workspace.git \
  refs/tags/v1.5.10 'refs/tags/v1.5.10^{}'
read -r -p 'Geprüfter vollständiger Commit von v1.5.10: ' tw_release_sha
~/.local/bin/trading-workspace update v1.5.10 "$tw_release_sha"
~/.local/bin/trading-workspace status
```

Der Updater prüft Tag, Commit und Version, sichert den privaten Zustand und baut
die vorhandenen Anwendungsimages aus dem geprüften Stand. Kein eigener neuer
Installations- oder Image-Publish-Weg ist erforderlich. Die anschließende
Statusausgabe muss Version 1.5.10, den vollständigen Zielcommit, gesunde Dienste
und Bereitschaft `ready` zeigen. Erst danach ist die neue Installation technisch
belegt; die lesende Kontrolle des Ergebnisberichts bleibt davon unterscheidbar.
