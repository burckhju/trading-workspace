## Was sich für die Bedienung ändert

Der Navigationseintrag **Realisierte Ergebnisse** öffnet
`/performance/realized-gross`. Gewählt werden der erste und letzte Kalendertag
einschließlich, eine ausdrückliche Berichtswährung und eine IANA-Berichtszeitzone.
Die sichtbare Vorgabe `Europe/Berlin` ist eine Berichtsentscheidung; sie ersetzt
keine gespeicherte Ausführungszone. Maßgeblich für die Zuordnung ist der
wirtschaftliche Verkaufszeitpunkt beziehungsweise das belegte Ausführungsdatum.

Die Ansicht zeigt wirksame Verkäufe eigener, nicht stornierter Trades. Auch
Teilverkäufe noch offener Trades zählen. Jeder verwendbare Beitrag wird mit dem
tatsächlichen Stückverkaufspreis und der unmittelbar vorher geltenden
Average-Cost-Basis berechnet. Der Quellen-Drill-down erklärt diese Basis anhand
der vollständigen vorherigen wirksamen Kauf- und Verkaufshistorie, auch vor dem
ausgewählten Zeitraum. Der heutige Produktname dient nur als Stammdatenanzeige.

Eine Berichtswährung bestätigt keine Buchungswährung. Dafür gibt es bei den
bestehenden Erfassungswegen eine bewusste Währungsbestätigung. In **Kauf- und
Verkaufsdaten** können vorhandene Ausführungen ausdrücklich bestätigt werden.
Eine Korrektur der wirtschaftlichen Buchung erhält eine eigene Ausführungs-ID
und benötigt ihre eigene Bestätigung. Eine spätere Währungsbestätigung ergänzt
die Herkunft nachvollziehbar; sie schreibt alte Kauf- oder Verkaufspreise nicht um.

| Anzeige | Bedeutung |
|---|---|
| Vollständig | Alle potenziell passenden Verkäufe sind geklärt; die Summe kann auch tatsächlich null sein. |
| Teilweise auswertbar | Es gibt verwendbare Beiträge und relevante Lücken. Die bekannte Teilsumme ist sichtbar, eine vollständige Gesamtsumme bleibt unbekannt. |
| Nicht berechenbar | Relevante Fälle sind vorhanden, aber kein qualifizierter Geldbeitrag. Es wird kein Nullbetrag als Ersatz ausgegeben. |
| Leere Auswahl | Keine passenden Verkäufe und keine relevante ungeklärte Zuordnung. Das ist von einem gemessenen Nullergebnis unterscheidbar. |

Die Summe umfasst alle verwendbaren Beiträge der Antwort, unabhängig von der
angezeigten Tabellenseite. Anzeige und gegebenenfalls Rundungsdifferenz werden
aus ungerundeten Beiträgen ermittelt. Bei Date-only erscheint keine erfundene
Mitternachtsausführung. Unklare Periodenzuordnung sowie unbekannte oder gemischte
Währungen bleiben sichtbar; eine automatische FX-Umrechnung findet nicht statt.

Eine neue Auswertung verwendet die jetzt wirksamen korrigierten Fakten über den
gewählten Zeitraum. Eine spätere Preis-, Datums- oder Währungskorrektur kann
deshalb eine neue Auswertung desselben Zeitraums verändern. Innerhalb einer
Antwort beruhen Summe, Zeilen, Zähler und Herkunft auf derselben Quellenbasis.
Beim erneuten Lesen wird ein Wechsel dieser Basis angezeigt. Es entsteht keine
persistente historische Berichtssitzung.

Das Ergebnis ist **brutto vor Gebühren, Kommissionen und Steuern**. Journal,
abgeschlossene Nachbeobachtung, Reviewstatus oder Lesson-Abschluss sind keine
Voraussetzung. Lesen erzeugt keine Buchungen oder Lernobjekte, führt keine
Revalidierung aus und fragt keine Livekurse ab.

## Migration und Betriebsfolgen

Die additive Migration
[`20261017_0047`](../../backend/migrations/versions/20261017_0047_execution_currency_confirmations.py)
folgt auf `20261014_0046`. Sie ergänzt die unveränderliche, nach Workspace,
Trade und konkreter Ausführung gebundene Bestätigungshistorie
`execution_currency_confirmations` sowie die dafür benötigten Constraints.
Der bestehende Updater führt `alembic upgrade head` aus; ein Stamp oder eine
manuelle Änderung bestehender Ausführungswerte ist nicht erforderlich.

**Kein EUR-Backfill:** Die Migration bestätigt keine historische Währung und
ändert keine bisherigen Preise, Mengen oder Ausführungsdaten. Alte Buchungen
ohne ausdrücklichen Beleg bleiben unbekannt. Auch ein bisher als EUR interpretiertes
Depot kann deshalb zunächst nur Teilsummen oder einen nicht berechenbaren Bericht
zeigen. Synthetische EUR-Tests belegen keine Währung realer Nutzerbuchungen.

Der Downgrade verweigert das Entfernen der Migration, sobald Bestätigungen
gespeichert sind. Die Herkunft darf nicht für einen Versionsrückschritt gelöscht
werden. Dies ist kein verlustfreier Rollback-Vertrag; Datenbank- und
Konfigurationssicherungen sowie die Wiederherstellung sind vor dem Update zu
bewerten. Der bestehende Updateweg bietet keinen automatischen Rollback.

Der neue Bericht arbeitet mit einer kurzen lokalen Lesetransaktion und
begrenzten Datenmengen. Die globale Transaktionsisolation bleibt unverändert.
Bei Überschreitung einer Lesegrenze oder einem Lesefehler wird kein gekürzter
Geldbetrag als vollständiger Bericht ausgegeben. Die genauen Ressourcen- und
Fehlergrenzen stehen in der
[Berichtsqualifikation](../implementation/PERIOD_REALIZED_GROSS_REPORT_QUALIFICATION.md).
Neue Providerzustimmungen, Modellaktivierungen und Änderungen privater
Compose-/Benachrichtigungskonfiguration gehören nicht zu dieser Auslieferung.

## Bestehende verwaltete Linux-Installation aktualisieren

Der [vorhandene Launcher](../technical/LINUX_LAUNCHER.md) verwendet weiterhin
`~/Boerse/trading-workspace-app` und den privaten Zustand in
`~/Boerse/trading-workspace-state`. Als bisheriger Linux-Benutzer ohne sudo
arbeiten. Offene Eingaben speichern, Status und freien Platz prüfen und die
vorübergehende Unterbrechung während Build und Migration einplanen:

```bash
~/.local/bin/trading-workspace status
df -h ~/Boerse
docker system df
```

Erst nach erfolgreicher Veröffentlichung den Tag direkt vom Repository lesen:

```bash
git ls-remote --tags https://github.com/burckhju/trading-workspace.git \
  refs/tags/v1.5.9 'refs/tags/v1.5.9^{}'
```

Der vollständige Tag-Commit muss mit dem erfolgreich geprüften main-Commit aus
den veröffentlichten CI-Läufen übereinstimmen. Falls eine zusätzliche `^{}`-Zeile
existiert, bezeichnet sie den aufgelösten Commit eines annotierten Tags. Ohne
veröffentlichten Tag oder passenden vollständigen Commit nicht aktualisieren.
Den so geprüften Commit an den installierten Updater übergeben:

```bash
read -r -p 'Geprüfter vollständiger Commit von v1.5.9: ' tw_release_sha
~/.local/bin/trading-workspace update v1.5.9 "$tw_release_sha"
```

Der Updater prüft Tag, Commit und VERSION erneut und erhält die gespeicherte
private Compose-Kette. Quellstand, Datenbank und Consent-Zustand werden gesichert.
Die Anwendungsimages werden aus dem geprüften Quellstand lokal gebaut; dieser
Auslieferungsweg benötigt keinen neuen Registry-Publish-Workflow. In der
verwalteten Installation kein nacktes `git pull` oder `start-linux.sh` als Ersatz
verwenden. Bei Abbruch mit `pending` zuerst den zugehörigen Versuch diagnostizieren;
keine Marker, Volumes oder Sicherungen löschen und keine `.env` überschreiben.

Die vom Launcher geprüften Helfer-Prüfsummen bleiben unverändert:
